# ODrive deployment & configuration

Chain: **Local → GitHub → Lovable → Cloudflare Workers**

## 1. Where each value lives

| Kind | Where it lives | Examples |
| --- | --- | --- |
| Non-secret config | `wrangler.toml` `[vars]`, `.env.example`, build-time `VITE_*` | `ENVIRONMENT`, `APP_URL`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` |
| Secret | Cloudflare Worker Secrets (`wrangler secret put NAME`) | `SUPABASE_SERVICE_ROLE_KEY`, `ODRIVE_ENCRYPTION_KEY`, `LOVABLE_API_KEY`, `LOVABLE_CRON_SECRET`, `*_CLIENT_SECRET` |

The full classified list is `src/config/runtime-env.server.ts` (`CONFIG_VARS` / `SECRET_VARS`).
Application code reads values through that module (`readConfig`, `readSecret`,
`requireSecret`) instead of touching `process.env` ad hoc.

Secrets are never placed in `[vars]`, never logged, never returned by an API,
and never exposed to the browser. Only `VITE_*` publishable values reach the
client bundle.

## 2. Git hygiene

- `.gitignore` excludes `.env.local`, `.env.production`, `.env.*.local`, `.dev.vars*`.
- `.env` in this repository is generated by Lovable Cloud and contains **only**
  the Supabase URL, project ref and publishable (anon) key — all browser-safe by
  design. It contains no service-role key, no OAuth secret, no database password.
- If a real secret is ever committed, rotate it immediately (new value in
  Cloudflare Secrets + revoke the old one at the provider) — deleting the commit
  is not enough.

## 3. Cloudflare secrets that survive redeploys

`wrangler deploy` **preserves existing Worker Secrets**. The values that used to
disappear were runtime *variables* set by hand in the dashboard; `keep_vars = true`
in `wrangler.toml` stops a deploy from clearing them.

One-time setup per environment:

```bash
wrangler secret put SUPABASE_SERVICE_ROLE_KEY
wrangler secret put ODRIVE_ENCRYPTION_KEY
wrangler secret put LOVABLE_API_KEY            # optional
wrangler secret put LOVABLE_CRON_SECRET        # optional
wrangler secret put GOOGLE_CLIENT_ID           # optional
wrangler secret put GOOGLE_CLIENT_SECRET       # optional
# staging:
wrangler secret put ODRIVE_ENCRYPTION_KEY --env staging
```

List configured names (names only, never values):

```bash
wrangler secret list
```

Bindings (R2, Hyperdrive, Queues) must be declared in `wrangler.toml` so they are
recreated on every deploy instead of being clicked together in the dashboard.

## 4. Deploy sequence

```bash
node scripts/check-config.mjs      # fails loudly on missing required config
bun run build
wrangler deploy                    # or: wrangler deploy --env staging
curl -s https://<your-domain>/api/public/health          # liveness
curl -s https://<your-domain>/api/public/health/ready     # dependencies
curl -s https://<your-domain>/api/public/health/config    # presence only, 503 if incomplete
```

`/api/public/health/config` returns `{ name, kind, required, present }` per
variable — booleans only, so it is safe to hit from CI or a monitor.

## 5. Verifying persistence

1. Deploy, then check `/api/public/health/config` → `"configured"`.
2. Push a change, let Lovable rebuild, redeploy, and check the same endpoint again.
3. Repeat once more. `wrangler secret list` should be unchanged across all three.
4. Confirm a clean clone can be configured without any secret in Git: copy
   `.env.example`, fill local values, and set production values via
   `wrangler secret put`.

## 6. Database portability

PostgreSQL stays behind `DatabaseAdapter` → `PostgresAdapter`
(`src/database/adapter.ts`, `src/database/postgres.server.ts`). That adapter file
is the only place that knows the Postgres host, so moving to another PostgreSQL
provider — or putting Cloudflare Hyperdrive in front of it — is a configuration
change, not a business-logic change. Hyperdrive must never be referenced from
domain code.
